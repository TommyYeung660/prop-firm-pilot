## Task 1: Fix TP/SL Notification Showing "0.00 lots" and "Trigger: 0.0" (Issue #4/#14, P2)

**Files:**
- Modify: `src/scheduler/scheduler.py:985-1213` (`_handle_position_closed`)
- Read: `src/decision_store/sqlite_store.py:714-721` (`get_decision`)
- Read: `src/decision/schemas.py:148` (`execution_meta` field)
- Test: `tests/test_scheduler.py` (add new test)

**Context:** When a position closes, `_handle_position_closed()` tries to fetch closed position details from MatchTrader API with 3 retries. If the API doesn't return data within retries, `volume`, `close_price`, `open_price` remain at 0.0 defaults. These zeros propagate to `alert_service.sl_tp_hit()` notifications. However, `execution_meta` (persisted as JSON by `engine.py` at line 374-392 when the position was opened) already stores `volume`, `sl_price`, `tp_price`, `fill_price`. We can use this as a fallback.

Also, `exit_reason` is inferred purely from PnL sign (`pnl > 0 → tp_hit`, `pnl < 0 → sl_hit`), which is incorrect when a position is manually closed in profit. With `execution_meta` we can compare `close_price` vs `sl_price`/`tp_price` (with pip tolerance) for more accurate classification.

## Task 3: Add Spread Gate Pass-Through for Missing Data (Issue #2 remaining, P2)

**Files:**
- Modify: `src/decision/tactical_validator.py:219-231` (`check_hard_gates`, spread section)
- Modify: `src/scheduler/scheduler.py:740-760` (`_fetch_tactical_data`)

**Context:** The spread gate fails with `spread_ratio=inf` in production because:
1. When the MatchTrader quote API call fails (exception at line 757 of scheduler.py), `current_spread` and `typical_spread` remain at their default 0.0.
2. The spread gate formula: `ratio = current_spread / typical_spread` → `0.0 / 0.0` → division by zero → `inf`.
3. Even when the quote succeeds, `typical_spread` = `avg_spread_pips * pip_size` = `1.5 * 0.0001` = `0.00015`, which is correct. But if instrument config is missing for a symbol, `typical_spread` stays 0.0.

The ATR gate already has a pass-through (v1.3.8), but the spread gate does not. We need:
1. Spread gate pass-through when data is unavailable (matching ATR gate pattern)
2. Per-instrument `avg_spread_pips` in YAML config (EURUSD=1.2, GBPUSD=1.5, USDJPY=1.3, AUDUSD=1.8)

## Task 4: Add Duplicate Symbol Guard for Stale Intent Race (Issue #9, P2)

**Files:**
- Modify: `src/execution/engine.py:91-141` (`execute_ready_intents` or `_execute_single_intent`)
- Modify: `src/scheduler/scheduler.py` (`_process_claimed_intent`, HOLD handling)
- Test: `tests/test_engine.py` (add new test)

**Context:** The HOLD→BUY bug is a stale intent race condition. Here's the sequence:
1. Scanner creates intent A for EURUSD → claimed → LLM decides BUY → marked `ready_for_exec`
2. Before execution loop runs, scanner creates intent B for EURUSD (same symbol, new scan)
3. Intent B → claimed → LLM decides HOLD → intent B cancelled (correct)
4. Execution loop picks up intent A (still `ready_for_exec` with BUY) and executes it
5. Result: HOLD decision should have overridden, but stale BUY intent ran

The fix has two parts:
1. In scheduler `_process_claimed_intent`: when HOLD is decided, also cancel any existing `ready_for_exec` intents for the same symbol (not just the current intent).
2. In execution engine: before executing, verify no newer intent for the same symbol has been created and decided HOLD.

## Task 6: Fix DuckDB Transaction Nesting Error (Issue #13, P3)

**Files:**
- Modify: `src/data/fx_duckdb_store.py:120-151` (`upsert`), `242-258` (`upsert_intraday`)
- Test: `tests/test_fx_duckdb_store.py` (add new test)

**Context:** DuckDB's Python driver auto-starts a transaction on the first write statement. Calling `BEGIN TRANSACTION` when a transaction is already active causes "cannot start a transaction within a transaction" error. Both `upsert()` (line 121) and `upsert_intraday()` (line 242) use explicit `BEGIN TRANSACTION`.

Fix: Remove explicit `BEGIN TRANSACTION` and `COMMIT`/`ROLLBACK`. Instead, use the connection's built-in transaction management. DuckDB executes each statement in auto-commit mode unless you explicitly start a transaction. Since we want atomicity (DELETE + INSERT), we keep the explicit transaction but guard against nesting.

**Step 1: Write the failing test**

```python
def test_upsert_no_transaction_nesting_error(tmp_path):
    """upsert should not fail with 'cannot start a transaction' error."""
    import duckdb
    import pandas as pd
    from src.data.fx_duckdb_store import FxDuckDbStore

    store = FxDuckDbStore(str(tmp_path / "test.duckdb"))
    df = pd.DataFrame({
        "date": [pd.Timestamp("2026-03-01")],
        "open": [1.08], "high": [1.09], "low": [1.07],
        "close": [1.085], "volume": [0],
    })

    # First upsert should work
    count = store.upsert("EURUSD", df, provider="test")
    assert count == 1

    # Second upsert (same data) should also work without transaction error
    count = store.upsert("EURUSD", df, provider="test")
    assert count == 1
```

**Step 2: Run test to verify**

Run: `uv run pytest tests/test_fx_duckdb_store.py::test_upsert_no_transaction_nesting_error -v`
Expected: May pass (since each call is independent). The real failure happens when DuckDB's connection has a pending transaction from a previous failed/incomplete operation.

**Step 3: Implement the fix**

In `src/data/fx_duckdb_store.py`, modify both `upsert()` and `upsert_intraday()`:

Replace the pattern:
```python
self._conn.execute("BEGIN TRANSACTION")
try:
    ...
    self._conn.execute("COMMIT")
except Exception as e:
    self._conn.execute("ROLLBACK")
    raise
```

With:
```python
try:
    if not self._conn.execute("SELECT current_setting('transaction_id')").fetchone():
        self._conn.execute("BEGIN TRANSACTION")
except Exception:
    pass  # Already in a transaction or setting not available

try:
    ...
    self._conn.execute("COMMIT")
except Exception as e:
    try:
        self._conn.execute("ROLLBACK")
    except Exception:
        pass  # Rollback may also fail if no active transaction
    logger.error("FxDuckDbStore: upsert failed for {}: {}", symbol, e)
    raise
```

Actually, the simplest and safest fix is to just wrap in try/except for the BEGIN:

```python
        # v1.3.9: Guard against transaction nesting — DuckDB may auto-start transactions
        try:
            self._conn.execute("BEGIN TRANSACTION")
        except duckdb.TransactionException:
            pass  # Already in a transaction — proceed with existing one
```

Import `duckdb` at the top of the file (already imported).

Apply the same pattern to both `upsert()` (line 121) and `upsert_intraday()` (line 242).
