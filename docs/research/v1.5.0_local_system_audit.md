# v1.5.0 長期盈利可行性 — 本地系統審查

> **建立日期**: 2026-03-15
>
> **審查對象**:
> - `prop-firm-pilot`
> - `qlib_market_scanner`
> - `TradingAgents`
>
> **目的**: 只根據目前本地可讀到的代碼與文件，判斷哪些能力已經存在，哪些仍停留在雛形、設計或高風險狀態。

---

## 1. 審查方法

- **事實**: 直接來自本地程式碼、README、roadmap、report。
- **推論**: 由架構與實作方式推導出的能力邊界。
- **重點**: 只看與長期盈利相關的五條線:
  - alpha
  - execution
  - risk / portfolio
  - learning / adaptation
  - validation

---

## 2. `prop-firm-pilot`

### 2.1 支持長期系統候選的事實

- **事實**: `src/main.py` 與 `src/scheduler/scheduler.py` 已形成 async scheduler + monitor + decision store 的持續運行模型，不再只是單次日內腳本。
- **事實**: `src/execution/engine.py` 在開倉前會抓 pre-trade quote，開倉後會記錄 `exec_latency_ms`、`slippage_pips` 與 execution metadata，並落到 `src/decision_store/sqlite_store.py` 的 `execution_meta`。
- **事實**: `src/decision/close_control_plane.py`、`src/decision/close_reconciler.py`、`src/scheduler/scheduler.py` 已把 tactical exit、reeval close、best-day close、reduce exposure 等 close 路徑收斂到單一 close-domain contract。
- **事實**: `src/scheduler/scheduler.py` 會把 `historical_pnl_context`、`market_event_context` 注入 agent context，並在平倉後呼叫 `self._agents.reflect(...)`，表示 learn loop 已經閉合。
- **事實**: `src/monitor/memory_journal.py` 與 `src/monitor/trade_journal.py` 能記錄 decision anchor、trade result、typed event；`src/optimize/tactical_entry_stats.py` 也能對 `TACTICAL_RESULT` 做 symbol / session / regime 聚合。
- **事實**: `src/compliance/prop_firm_guard.py`、`src/monitor/equity_monitor.py`、Best Day Tracker 與 write-budget 控制已形成強化的帳戶保護層。

### 2.2 限制長期盈利可信度的事實

- **事實**: `src/execution/position_sizer.py` 的 sizing 核心仍是單筆風險百分比與 stop distance；沒有 base / quote exposure budget，也沒有 correlation-aware sizing。
- **事實**: roadmap `docs/PropFirmPilot_v1.4.0_road_map.md` 明確寫出 `缺少 portfolio-level exposure budget`、`缺少高相關倉位控制`、`缺少 diversification policy`。
- **事實**: 記憶資料目前同時散落在 `TradeJournal` JSONL、`MemoryJournal` Markdown、TradingAgents Chroma memory、DecisionStore execution_meta，尚未看到單一 trade-memory schema。
- **事實**: `OptimizationEngine` 目前主要做 win-rate / inactivity / feedback PnL 門檻調整，還不是完整的 alpha validation engine。
- **事實**: 系統已具備很多 tactical / operational instrumentation，但還沒有看到「整體系統層級」的 cost-adjusted walk-forward 或 live-vs-backtest consistency gate。

### 2.3 推論

- **推論**: `prop-firm-pilot` 已非常接近 production control plane，但它更像是 execution-and-ops core，而不是已經證明有穩定 alpha 的完整 portfolio system。
- **推論**: 如果只看 execution integrity，成熟度已高於一般 PoC；但若看長期盈利，portfolio 與 validation 仍是硬缺口。

## 3. `qlib_market_scanner`

### 3.1 支持長期系統候選的事實

- **事實**: `src/config.py`、`README.md`、`src/pipeline/runner.py` 顯示 scanner 已支援 `fx` profile，並能跑 `1d`、`1h`、`4h`。
- **事實**: `src/pipeline/qlib_workflow.py` 實作了 label、dataset、dynamic cost、backtest metrics、confidence metrics、Top-K export、EMA smoothing。
- **事實**: `src/pipeline/dynamic_costs.py` 具備 FX spread cost function，表示研究層已開始把成本納入，而不只是裸訊號。
- **事實**: `src/experiments/experiment_walk_forward_inprocess.py` 與 `src/experiments/experiment_cost_turnover_sensitivity.py` 顯示此 repo 已有 walk-forward 與 cost / turnover sensitivity 的研究腳手架。
- **事實**: output schema 已包含 `score`、`confidence`、`score_gap`、`drop_distance`、`topk_spread`，對下游 contract 有幫助。

### 3.2 限制長期盈利可信度的事實

- **事實**: `src/config.py` 的 `FX_TICKERS` 仍是固定 4 個 majors，對 FX 來說 universe 太小，難以支撐強的 cross-sectional alpha 主張。
- **事實**: `src/pipeline/runner.py` 與 `src/pipeline/qlib_workflow.py` 對 `4h -> day`、`1h -> 1min` 做 Qlib compatibility mapping，代表 intraday FX 支援存在技術折衷。
- **事實**: intraday 預設日期範圍約 1 年，對 regime diversity 來說仍偏短。
- **事實**: 雖然有 walk-forward 與 cost sensitivity 腳本，但尚未看到「已固定成 release gate」的研究紀律。
- **事實**: 此 repo主要證明「可以做研究」，不是「已證明 production alpha 穩定成立」。

### 3.3 推論

- **推論**: `qlib_market_scanner` 是本系統最像正式量化研究底盤的部分，但現階段比較像 promising research scaffold，而不是足以支撐長期盈利宣稱的 alpha engine。
- **推論**: 若不擴 universe、標籤設計、regime segmentation 與 OOS validation，scanner 只能提供候選合理性，不能提供長期盈利可信度。

## 4. `TradingAgents`

### 4.1 支持長期系統候選的事實

- **事實**: `tradingagents/graph/trading_graph.py` 支援 `session_id`、`market_type`、QLib context 注入，以及 `retrieved_trade_lessons` 的檢索。
- **事實**: `tradingagents/agents/utils/agent_states.py` 已有 `qlib_score`、`qlib_confidence`、`historical_pnl_context`、`market_event_context`、`retrieved_trade_lessons` 欄位。
- **事實**: `tradingagents/agents/utils/memory.py` 以 Chroma persistent memory + embedding 檢索為基礎，可做跨回合記憶。
- **事實**: `tradingagents/agents/analysts/market_analyst.py` 對 FX 提供 1D + 4H 的 intraday-aware prompt 與工具路徑。
- **事實**: `prop-firm-pilot` 的 `src/decision/agent_bridge.py` 會把 session-id、memory path、AB model routing、decision validation 與 refusal detection 包起來，降低直接整合風險。

### 4.2 限制長期盈利可信度的事實

- **事實**: `TradingAgents/README.md` 明確寫明框架設計用於研究目的，交易表現受模型、溫度、交易週期、資料品質與其他非確定性因素影響。
- **事實**: `tradingagents/default_config.py` 的預設 `market_type` 仍是 `us_stock`。
- **事實**: repo 內仍大量保留 `fundamentals`、`options`、`institutional`、`insider`、stock dataflows 與報告欄位，顯示結構仍強烈承襲 stock-first 設計。
- **事實**: 雖然 `market_analyst.py` 已加 FX prompt，但整個 graph 與 report utils 仍普遍保留 fundamentals/options sections。
- **事實**: `FinancialSituationMemory` 是 embedding 相似度檢索，尚未看到嚴格的 setup / session / regime schema gate，也尚未看到 deterministic replay 機制。

### 4.3 推論

- **推論**: TradingAgents 對本系統最合理的定位，是 high-context decision overlay，而不是能獨立承擔長期 alpha 的 deterministic core。
- **推論**: 如果不把其輸出限制在標準化風險語義、可審計欄位與低延遲節奏內，LLM 層會成為 profitability claim 的主要不確定來源。

## 5. 綜合審查

### 5.1 已存在的正面底盤

- execution integrity 已有明顯工程基礎
- close-domain audit trail 已顯著成熟
- scanner repo 有真正的量化研究腳手架
- memory / reflection / pnl feedback 已閉合成初步 learning loop
- async scheduler + observability + incident replay 已不像純研究原型

### 5.2 仍然缺失的硬能力

- portfolio-level exposure budget
- correlation / concentration guard
- 統一 trade-memory schema 與 memory quality gate
- 成本後 alpha 的 system-level OOS 證據
- LLM layer 對 intraday FX 的低延遲、低漂移、可重現驗證

### 5.3 審查結論

- **結論**: 本地代碼已證明本系統不只是 PoC，也不只是把三個 repo 粗暴串起來。
- **同時結論**: 目前最強的是 control plane，不是 profitability evidence。
- **因此**: 若要回答「能不能成為長期盈利系統」，目前只能說方向有局部合理性，但還缺 portfolio 與 validation 兩個最關鍵的可信度支柱。
