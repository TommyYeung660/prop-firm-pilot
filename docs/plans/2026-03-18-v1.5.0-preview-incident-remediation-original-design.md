# v1.5.0 Preview Incident Remediation Design

> Historical design artifact preserved from local `main` during remediation merge preparation.

**Date:** `2026-03-18`

**Goal:** 修正 `v1.5.0_preview` production incident 中已確認的 P0/P1 問題，優先恢復正確的交易決策鏈，並將 market-data architecture 從 `websocket-first` 調整為 `broker-quote-first + API-bars-first + websocket-auxiliary`。

## Context

本次 production incident 已確認的核心問題如下：

- `Best Day Rule` 在 `0` 成交、`0` 當日 PnL 的情況下仍拒單
- compliance headroom 檢查放得太後，導致必定被拒的單子仍完整跑過 LLM 與 tactical retry
- USDCAD tactical gate 長時間 `0% pass`
- EODHD websocket 在 incident 視窗內反覆退化
- `scanner.bundle.target_date_missing` 暴露出 pipeline success semantics 過寬
- Telegram outbound alert 在 incident 期間多次 `ReadTimeout`

本輪設計另外加入新的決策邊界：

- `P1` 的 market-data action 只基於 `prod_logs_20260318_v1.5.0_preview` 這包 evidence
- 若 websocket 一旦退化，就不再維持 websocket-first
- 但 `EODHD LIVE API` 有 `1 minute delayed` 限制，因此不能直接拿來取代 live quote / spread

## Non-Goals

- 不在本輪引入新的外部 market-data provider
- 不做完整 portfolio/risk engine 重寫
- 不在本輪新增多通道 paging platform；alerting 先保留 Telegram 為 primary，補 secondary sink 即可
- 不以這一輪直接優化策略 alpha；重點是修正錯誤 gate 與資料路徑
- 不把 delayed API 生硬拿來當 live quote

## Chosen Approach

### 1. P0: Best Day Rule 改為 actual-PnL-only

`Best Day Rule` 對新單的 pre-trade gating 改為只看「已發生的當日 PnL」：

- `daily_pnl = realized + unrealized`
- 不再把尚未開倉新單的 `hypothetical TP potential profit` 算入拒單條件

原因：

- production evidence 已證明現行 `projected_daily_pnl = current_daily_pnl + potential_profit` 會在 `0` 成交日錯殺新單
- 這違反本案的業務定義
- 真正接近 Best Day cap 的管理，應由 `BestDayTracker` 與 execution-side actual-PnL gate 處理，而不是用未發生的理論獲利前置拒單

### 2. P0: compliance headroom 前移到 candidate / intent admission

將「必定被拒」的 headroom 檢查從 execution 前移到 scheduler admission path：

- candidate admitted 前先計算當前 actual daily PnL headroom
- 若已接近 Best Day / drawdown / position cap，就直接 skip candidate
- intent 不建立，LLM 不執行，tactical retry 不啟動

這不是替代 execution compliance，而是把 deterministic reject 提前淘汰，降低 churn。

### 3. P0: tactical gate 校準與可觀測性

USDCAD tactical gate 在 incident 視窗內的真實狀態是：

- `spread.fail.ratio_too_wide`
- `atr.fail.insufficient_1h_data`
- `data_freshness` 多數時候反而是 pass

因此本輪不是只改一個 threshold，而是分兩塊：

- 檢查 `< 2.0x` spread ratio limit 是否對 USDCAD 過嚴
- 檢查 `1h` ATR 暖機資料為什麼在 live run 長時間不足

設計上新增明確校準與診斷輸出，區分：

- spread misfit
- ATR warmup deficiency
- quote freshness failure

### 4. P1: market-data architecture 改為 hybrid API-first

新的主路徑如下：

- `live quote / spread / pre-trade price reference`: `MatchTrader get_quote()` primary
- `closed 1m/5m/1h bars`: EODHD REST API primary
- `EODHD websocket`: auxiliary only

這不是純 API-first，而是混合式：

- bars 確實改為 API-first
- live quote 不能用 delayed API，改由 broker quote-first
- websocket 降級為輔助快取、遙測、觀察，不再承擔 primary trading data source

### 5. P1: websocket degraded semantics 改寫

目前 websocket 一退化，系統容易放大成整體 market-data 事故。新設計要求：

- websocket degraded 不等於 system unusable
- 只要 broker quote 可用、API bars 可用，交易系統仍可運行
- degraded mode 應以 operator-visible summary 呈現
- block entry 的條件應基於真正不可用的 primary path，而非 auxiliary websocket state

### 6. P1: scanner pipeline success contract 收緊

`pipeline finished successfully` 只有在以下條件同時成立時才算 success：

- pipeline process 成功完成
- output bundle 含 `target_date`
- live ingestion 能成功讀入該 `target_date`

否則應回報 `incomplete` 或 `bundle_invalid`，不能再當成成功。

### 7. P1: alerting resilience 補強

現有 `AlertService` 已有部分 circuit behavior，但 incident 仍出現多次 outbound `ReadTimeout`。本輪設計要求：

- outbound send retry 要有更清楚的 accounting
- send failure 要可計數、可告警
- 增加 secondary sink，避免 Telegram timeout 時完全靜默

## Data Flow After Change

### Trade Entry Data Path

1. Scheduler 取得 scanner candidate
2. Admission guard 先做 actual-PnL-based compliance headroom 檢查
3. 若通過才建立 intent
4. LLM 決策後進 tactical validation
5. Tactical validation 讀：
   - broker quote for spread / freshness baseline
   - API bars for 1m/5m/1h closed bars
6. execution 前再跑 final compliance checks

### Market Data Path

- `Quote Path`: MatchTrader primary
- `Bar Path`: EODHD API primary
- `Auxiliary Telemetry`: EODHD websocket

## Reliability Analysis Requirement

在改 market-data architecture 前，先新增一個 bundle-analysis script，只基於當前 incident bundle 做 evidence extraction：

- websocket failure count
- REST fallback count
- fallback bar stale-age distribution
- market-data entry blocks
- quote freshness pass/fail ratio
- tactical provenance distribution

雖然本輪設計已預設 websocket 不再當 primary，但仍需把 evidence 產出為可重跑的診斷腳本，而不是只留在一次性人工分析。

## Safety Properties

- 不會因 hypothetical profit 再次在 `0` 成交日觸發 Best Day reject
- compliance final gate 仍保留，不因前移 admission 而取消 execution-side protection
- delayed API 不會被錯用於 live quote / spread
- websocket 可以失敗，但不應再直接拖垮 primary trading data path
- scanner 不會再把缺少 `target_date` 的 bundle 報為 success

## Testing Strategy

1. `Best Day` regression tests
   - `daily_pnl=0`、`open_positions=0`、高 potential TP 時不得因 Best Day 拒單
   - execution-side actual-PnL gate 在接近 cap 時仍可正確阻止新單

2. Admission guard tests
   - near-limit 時 candidate 被 skip，而不是建立 intent 後才 reject

3. Tactical diagnostics tests
   - 明確記錄 spread / atr / freshness 的獨立失敗原因

4. Market-data routing tests
   - broker quote primary
   - API bars primary
   - websocket degraded 時仍能繼續走 primary path
   - broker quote unavailable 才 block entry

5. Scanner success-contract tests
   - `pipeline finished` 但 target date 缺失時必須回傳 invalid/incomplete

6. Alerting resilience tests
   - Telegram send timeout 觸發 retry / metrics / secondary sink

## Rollout Notes

- 先完成 `P0` 並上線，因為這些問題即使 market data 完全健康也會持續殺死交易流程
- market-data re-architecture 以 feature-flag 或 staged rollout 方式切換，避免一次性全面翻轉
- 上線後第一階段重點觀察：
  - Best Day rejection 是否歸零
  - candidate-to-intent conversion 是否更乾淨
  - tactical pass rate 是否從 `0%` 脫離
  - broker quote API 使用量是否在可接受範圍內
