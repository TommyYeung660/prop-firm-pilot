# v1.4.8 Close Control Plane Design

**Version Target:** `v1.4.8`

**Goal:** 將所有 close 類路徑收斂成單一 close control plane，讓 `tactical exit`、`emergency close`、`reduce exposure`、`best-day close`、`LLM re-eval close`、以及 `manual/broker-side detected close` 都能用同一套 execution、read-back、journal、alert、reconciliation 語義運作。

**Scope:** 聚焦 `prop-firm-pilot` 的 close execution integrity、action provenance、journal consistency、close reason reconciliation；不新增新的交易策略，不擴張 tactical exit 閾值，不修改 compliance math。

---

## 1. 背景與問題

roadmap 已將 `v1.4.8` 定義為 **Tactical Exit Fixes & Optimization**，重點是：

- exit correctness
- replayability
- journal consistency
- broker read-back verification

目前系統已經有 tactical exit manager、drawdown reduce exposure、emergency close、best-day protection、以及 LLM re-evaluation close 路徑，但 close-domain 仍是分裂的：

1. broker write path 分散在 `Scheduler` 多個 method
2. `modify/partial/full close` 的 read-back 邏輯不一致
3. `TACTICAL_EXIT_*`、`EQUITY_*`、`TRADE_CLOSED` journal event 各自定義 payload
4. `_handle_position_closed()` 會再做另一套 final reason 推斷，和主動 close 路徑沒有單一事實來源
5. `DecisionStore.exit_reason` 目前混合承載「誰觸發」與「最終怎麼關」

結果是：

- 同一筆倉位的「發起來源、實際送單、broker read-back、最終平倉原因」可能分裂在多個 event
- tactical modify 已送達但 verify mismatch 時，無法和真正未送達清楚區分
- partial close 和 full close 的 lifecycle 不夠一致
- external/manual close 只能在 position monitor 後補判斷，缺乏和主動 close 路徑一致的 provenance

---

## 2. 設計目標

### 2.1 Functional Goals

- 所有 close 類來源都先映射成同一套 `CloseIntent`
- 所有 broker write / verify 結果都映射成同一套 `CloseOutcome`
- 所有最終平倉事實都由同一個 reconciler 產生 canonical `final_close_reason`
- partial close、full close、modify-only、external detected close 具備固定語義
- 任一倉位都能回放出完整 close audit trail

### 2.2 Engineering Goals

- 保持 `Scheduler` 為 orchestration 層，不把 close-domain 細節繼續堆進去
- 對 `DecisionStore.exit_reason` 保持向後相容
- 優先形成單一 close audit schema，再做後續優化
- 讓 postmortem、alert、memory、metrics 共用同一份 close 事實模型

### 2.3 Non-Goals

- 不新增新的 tactical exit 規則或閾值
- 不把 broker client 改成承載 close semantics
- 不在 `v1.4.8` 直接做 `DecisionStore` schema migration
- 不把 `v1.4.8` 擴張成完整 event-sourced trading state machine

---

## 3. Architecture / Scope Boundary

`v1.4.8` 採 **CloseControlPlane** 架構，而不是單純在 `Scheduler` 增加更多 helper。

### 3.1 Why CloseControlPlane

這一版的核心問題不是 exit rule 不夠多，而是 close-domain 的 execution integrity 和 audit trail 不夠統一。

因此 `v1.4.8` 的責任不是擴張策略，而是把以下路徑收斂進同一控制面：

- `tactical_exit`
- `emergency_close`
- `reduce_exposure`
- `best_day_close`
- `reeval_close`
- `manual/broker-side detected close`

### 3.2 Scope Rule

本版只做一件事：

> 用單一 close control plane，把所有 close 類來源收斂成統一的 execution、read-back、journal、reconciliation 模型。

也就是說：

- entry control plane 留在 `v1.4.7`
- 完整 trading state machine integration 留在 `v1.4.9`

---

## 4. Canonical Data Model

### 4.1 Three-Layer Close Semantics

本版明確拆開三個概念：

1. `trigger_source`
   - 誰發起這個 close-domain action
   - 例如：`tactical_exit`、`emergency_close`、`reduce_exposure`、`best_day_close`、`reeval_close`、`manual_or_broker`

2. `action_kind`
   - 系統當下試圖做什麼
   - 例如：`modify_only`、`partial_close`、`full_close`、`close_all`、`external_detected_close`

3. `final_close_reason`
   - 這筆倉位最後是怎麼結束的
   - 例如：`tp_hit`、`sl_hit`、`tactical_exit`、`best_day_close`、`reeval_close`、`manual_close`、`broker_stopout`

### 4.2 `CloseIntent`

`CloseIntent` 代表一個 close-domain command。最少包含：

- `trigger_source`
- `action_kind`
- `position_id`
- `intent_id`
- `symbol`
- `side`
- `requested_volume`
- `requested_sl`
- `requested_tp`
- `reason_code`
- `source_context`

### 4.3 `CloseOutcome`

`CloseOutcome` 代表 control plane 對 `CloseIntent` 的執行結果。最少包含：

- `trigger_source`
- `action_kind`
- `execution_status`
- `broker_result`
- `readback_status`
- `final_close_reason`
- `journal_payload`
- `meta_patch`

### 4.4 Backward Compatibility

為了不打斷現有統計與 guard：

- `DecisionStore.exit_reason` 保留，語義固定等於 `final_close_reason`
- `trigger_source`、`action_kind` 先寫入 `execution_meta["close_control"]` 與 journal
- 現有 `sl_hit/tp_hit/manual_close/best_day_close/reeval_close` 依賴不被破壞

---

## 5. Control Plane Data Flow

### 5.1 CloseIntent Builders

各上游模組仍保有「為什麼要動作」的判斷責任，但不再直接操作 broker。

- tactical exit path 產生 `trigger_source=tactical_exit`
- drawdown reduce exposure 產生 `trigger_source=reduce_exposure`
- emergency close 產生 `trigger_source=emergency_close`
- best-day protection 產生 `trigger_source=best_day_close`
- LLM re-eval reversal 產生 `trigger_source=reeval_close`
- position monitor 偵測外部關倉時產生 `trigger_source=manual_or_broker`

### 5.2 `CloseControlPlane.execute()`

`execute()` 負責統一 broker write path：

- `modify_only` -> `modify_position + verify_sl_tp`
- `partial_close` -> `close_position(volume < current_volume)`
- `full_close` -> `close_position(volume == current_volume)`
- `close_all` -> 展開成 per-position child intents
- `external_detected_close` -> 不做 broker write，只建立 reconcile-ready outcome

這一步只回答：

- 系統有沒有成功送出
- broker write 是否成功
- read-back 是否 verified / mismatch / pending

這一步不直接決定 `final_close_reason`。

### 5.3 `CloseReconciler.reconcile()`

`CloseReconciler` 統一接手目前 `_handle_position_closed()` 的最終事實生成：

- 合併 broker closed position facts
- 合併 pending `CloseOutcome`
- 合併 execution_meta 與既有 fallback
- 產出 canonical：
  - `trigger_source`
  - `action_kind`
  - `final_close_reason`
  - `resolution_path`
  - journal payload
  - `execution_meta` patch
  - `DecisionStore.exit_reason`

### 5.4 Design Effect

這讓下列情境可以被正確表達：

- tactical modify 成功，但最後被 SL 打掉
  - `trigger_source=tactical_exit`
  - `action_kind=modify_only`
  - `final_close_reason=sl_hit`

- reeval 發出 full close 並最終平倉
  - `trigger_source=reeval_close`
  - `action_kind=full_close`
  - `final_close_reason=reeval_close`

- broker/manual close 被動偵測
  - `trigger_source=manual_or_broker`
  - `action_kind=external_detected_close`
  - `final_close_reason` 依 broker facts / price proximity / fallback PnL 決定

## 6. Error Handling And Reconciliation Policy

### 6.1 Modify Actions

對 `MOVE_TO_BREAKEVEN`、`TRAIL_SL`、`REPRICE_TP`：

- 若 `modify_position` 失敗：
  - `execution_status=skipped`
  - `readback_status=not_needed`
  - 不回寫 tactical success meta

- 若 `modify_position` 成功但 `verify_sl_tp` 失敗：
  - `execution_status=verify_failed`
  - `readback_status=mismatch`
  - journal 必須能區分這是 verify mismatch，而不是單純沒送達
  - 不把 action 當作成功完成

- 若 verify 成功：
  - `execution_status=accepted`
  - `readback_status=verified`
  - 才更新 `breakeven_sl` / `trailing_sl` / `dynamic_tp`

### 6.2 Close Actions

對 `partial_close`、`full_close`、`close_all child`：

- broker write 成功後只記為：
  - `execution_status=submitted`
  - `readback_status=pending_reconcile`

- 真正的 `reconciled_partial` / `reconciled_closed` 必須等 position monitor / broker closed facts 收斂後再結案

### 6.3 Duplicate Close Guard

同一 `position_id` 若已有未結案 close intent：

- 一般 `full_close` / `partial_close` / `reeval_close` 不得重複送單
- `emergency_close` 允許覆蓋較低優先級 pending close

這避免 tactical、reeval、drawdown path 對同一倉位競爭送 close。

### 6.4 Partial Close Semantics

partial close 不等於 trade closed。

- partial close reconcile 後只更新剩餘倉位狀態
- journal 必須記錄原 volume、closed volume、remaining volume
- `DecisionStore.exit_reason` 不應因 partial close 被改成 close reason

### 6.5 External / Manual / Broker-Side Close

若 position 消失但沒有 pending close intent 命中：

- 建立 `trigger_source=manual_or_broker`
- `action_kind=external_detected_close`
- `final_close_reason` 再由 broker close facts、close price、SL/TP proximity、fallback PnL 推斷

### 6.6 Final Close Reason Priority

`final_close_reason` 的優先序如下：

1. 明確系統觸發：
   - `emergency_close`
   - `best_day_close`
   - `reeval_close`

2. broker 價格事實：
   - `tp_hit`
   - `sl_hit`
   - `broker_stopout`

3. 其他：
   - `manual_close`

## 7. Module And File Design

### 7.1 New Modules

- `src/decision/close_models.py`
  - 放 `CloseIntent`、`CloseOutcome`、typed close schemas

- `src/decision/close_control_plane.py`
  - 統一 broker write path
  - 封裝 normalization、verify、duplicate close guard、outcome 產生

- `src/decision/close_reconciler.py`
  - 根據 broker closed facts 與 pending outcomes 產生 canonical close facts

### 7.2 Modified Modules

- `src/scheduler/scheduler.py`
  - 改為建立 `CloseIntent` 並呼叫 control plane
  - `_handle_position_closed()` 改為委派給 reconciler

- `src/monitor/trade_journal.py`
  - 補 close control 相關 typed helper
  - 統一 close-domain journal schema

- `src/decision/tactical_exit_manager.py`
  - 保持 rule orchestration，不處理 broker semantics
  - 只提供足夠資訊讓 scheduler 建立 `CloseIntent`

- `tests/`
  - 新增 `tests/test_close_control_plane.py`
  - 新增 `tests/test_close_reconciler.py`
  - 擴充 tactical exit / reeval / scheduler 既有測試

### 7.3 Explicitly Out Of Scope

- 不把 close-domain 邏輯塞進 `matchtrader_client.py`
- 不做 `DecisionStore` schema migration
- 不在 `v1.4.8` 新增策略層規則或 thresholds

---

## 8. Acceptance Criteria

`v1.4.8` 完成後，必須滿足：

1. 任一 close 類動作都能產生單一、完整 close audit trail
2. `DecisionStore.exit_reason` 仍可供現有 `sl_hit/tp_hit` 統計使用
3. tactical exit、reeval、best-day、reduce exposure、emergency close 的 journal schema 統一
4. duplicate close 有明確去重與優先權規則
5. partial close 和 full close 的 reconcile 結果明確區分
6. modify action 的 verify mismatch 可被清楚審計

---

## 9. Expected Monday Runtime Effects

若 `v1.4.8` 按設計落地，週一 live run 應能直接觀察到：

- `TRAIL_SL` / `MOVE_TO_BREAKEVEN` 已送達但 verify mismatch 時，能明確區分為 execution-integrity 問題
- `tactical_exit`、`reeval_close`、`drawdown` 同時關注同一倉位時，不會重複 close
- external/manual close 不再只留下模糊 `manual_close`，而是先有 `manual_or_broker` provenance，再收斂出最終 reason
- `v1.4.9` 可以專注在 `v1.4.7` / `v1.4.8` 的 bugfix 和微調，而不是回頭補 close provenance 與 journal consistency

---

## 10. Summary

`v1.4.8` 的本質不是再增加更多 exit 規則，而是建立一個可審計、可回放、可 reconciliation 的 close control plane。

這讓系統之後能同時回答三個問題：

- 是誰發起了這次 close action
- 系統實際做了什麼 broker write / verify
- 這筆倉位最後到底是怎麼結束的

這三件事在現況中仍是分裂的；`v1.4.8` 的目標就是把它們收斂成單一事實來源。
