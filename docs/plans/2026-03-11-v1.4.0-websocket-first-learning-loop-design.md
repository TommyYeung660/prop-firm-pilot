# v1.4.0 WebSocket-First Learning Loop Design

**Date:** 2026-03-11  
**Version Target:** v1.4.0  
**Repos:** `prop-firm-pilot` + `TradingAgents`

---

## Goal

Implement `v1.4.0` as a cross-repo upgrade that:

1. makes market data ingestion **WebSocket-first**
2. keeps REST only for broker state, news, cold-start backfill, and fallback
3. closes the learning loop from realized trade outcome back into TradingAgents memory and future decisions

This is an **aggressive rollout**: WebSocket features are enabled by default and become the primary market-data path.

---

## Scope

### In Scope

- New EODHD FX WebSocket client in `prop-firm-pilot`
- In-memory tick, quote, and aggregated bar pipeline (`1m -> 5m -> 1h`)
- WebSocket-first integration for observe/volatility/tactical data reads
- REST fallback for feed staleness, disconnects, and cold-start backfill
- Richer reflection payload from closed trades
- Persistent memory write + retrieval injection in `TradingAgents`
- `v1.4.0` changelog and report updates

### Out of Scope

- Replacing MatchTrader broker REST APIs
- Replacing news APIs with streaming news
- Full event-driven execution rewrite
- Dashboard / visualization work

## Architecture

### 1. prop-firm-pilot: WebSocket-First Market Data

Add a primary market-data path based on EODHD FOREX WebSocket.

New components:

- `src/data/fx_websocket_client.py`
  - connect/auth/subscribe
  - heartbeat + reconnect
  - per-symbol last tick cache
  - callback dispatch to downstream aggregators/observers
- `src/data/fx_tick_aggregator.py`
  - convert ticks into:
    - latest quote
    - rolling volatility observations
    - closed `1m` bars
    - derived `5m` / `1h` bars from `1m`
- `src/data/market_data_hub.py`
  - unified read interface for:
    - latest quote
    - quote freshness
    - recent bars by timeframe
    - feed status / stale symbols
  - decides whether reads come from WebSocket cache or REST fallback

Existing runtime components will read market data from this hub first, not directly from EODHD REST.

### 2. prop-firm-pilot: Scheduler / Observe Integration

`Scheduler` becomes WebSocket-first for market observation.

- volatility detection shifts from periodic REST quote polling to tick-driven rolling state
- tactical validation reads spread/freshness/intraday bars from local stream cache when available
- `NewsEventTrigger` remains active and combines with WebSocket-driven observe signals
- immediate equity refresh behavior from `v1.3.9c` stays in place

Execution and broker truth remain unchanged:

- MatchTrader REST stays authoritative for positions, orders, and equity
- EODHD WebSocket only owns market quotes and locally aggregated bars

### 3. Cross-Repo Learning Loop

`prop-firm-pilot` produces richer structured post-trade feedback.

`TradingAgents` consumes that feedback in two ways:

1. **reflection persistence**
   - store trade outcome, context, and lesson in persistent memory
2. **decision-time retrieval**
   - retrieve similar historical situations before the next decision
   - inject retrieved lessons into analysis/trader prompts

This upgrades the current state from "reflect API exists" to "stable data-in, persistent memory, and retrieval-influenced future decisions."

## Data Flow

### Startup Flow

1. `Scheduler.start()` initializes market-data hub and WebSocket client.
2. REST cold-start backfill loads recent historical data for required symbols/timeframes.
3. Aggregator seeds rolling windows and initial closed bars.
4. WebSocket starts receiving live ticks.
5. Runtime switches to WebSocket-first reads for fresh data.

### Tick Flow

For every tick:

1. update latest quote cache
2. append to rolling volatility window
3. update active `1m` bucket
4. close `1m` bars on boundary
5. aggregate closed `1m` bars into `5m` and `1h`
6. notify scheduler observers when thresholds or anomalies are crossed

### Scheduler Event Flow

Observe inputs:

- WebSocket volatility events
- feed stale/degraded events
- news-trigger events

Actions triggered from those inputs may include:

- rescan scheduling
- immediate equity check
- market event context refresh
- tactical data refresh

### Trade Reflection Flow

On position close, `prop-firm-pilot` builds a structured reflection payload containing:

- symbol
- side
- realized PnL
- close reason
- recent market regime summary
- relevant market event context
- decision summary / risk meta

That payload is sent through `AgentBridge.reflect(...)`, then persisted in `TradingAgents` memory. Future decisions query for similar situations and inject the lessons into the prompt context.

## Fallback Design

### WebSocket-First, Not REST-Zero

REST remains available for:

- broker operations (`MatchTrader`)
- news polling
- cold-start historical backfill
- stale/disconnected feed fallback

### Symbol-Level Fallback

Fallback must operate per symbol where possible.

If one symbol becomes stale:

- mark that symbol `feed_stale`
- use REST-backed quote/bar refresh for that symbol only
- continue using WebSocket for healthy symbols

If the whole feed is degraded:

- switch market-data hub into `rest_fallback` mode
- keep system trading-capable with reduced timeliness

### Freshness Rules

Track separately:

- quote freshness
- active feed connectivity
- last tick per symbol
- closed-bar freshness

Indicators and tactical gates only consume **closed bars**, never partially formed bars.

---

## Error Handling

### Feed States

Expose explicit operational states:

- `connected`
- `degraded`
- `rest_fallback`
- `stale_symbols`

These states must be observable by scheduler logic and alerting, not only logged.

### Safe Failure Principles

- feed/aggregation failures must not block broker workflows
- reflection failures must not block post-trade lifecycle completion
- memory retrieval failures must degrade to "no lesson injected", not decision failure
- reconnect loops must use bounded exponential backoff

### Learning Loop Failure Isolation

Reflection is best-effort:

- async side effect after close
- logged on failure
- retryable with bounds
- never allowed to break position-close handling

## Rollout

This version is intentionally aggressive.

Config remains available for rapid rollback, but defaults are enabled:

```yaml
websocket:
  enabled: true
  use_as_primary_market_data: true
```

Operational meaning:

- production boots with WebSocket as primary market-data path
- REST remains a fallback and cold-start mechanism
- rollback can be done by config change instead of emergency code change

---

## Success Criteria

`v1.4.0` is considered complete when:

1. WebSocket becomes the default primary market-data source
2. volatility/tactical observe paths read from WebSocket-derived local state first
3. REST fallback works for stale/disconnected conditions
4. closed-trade outcomes are persisted into TradingAgents memory with usable context
5. future decisions can retrieve and inject relevant historical lessons
6. docs, tests, and regression evidence are updated for `v1.4.0`
