# v1.4.8 Report Design

**Version Target:** `v1.4.8`

**Goal:** 撰寫 `docs/PropFirmPilot_v1.4.8_Report.md`，用與 `v1.4.7` 報告一致的 `Part A / B / C / D` 結構，將 `Close Control Plane` 的實際運作語義、12 個細顆粒交易情景、可持續學習性、audit trail，以及對 `v1.4.9` / `v1.5.0` 的基線價值整理成一份可供 operator / architect 直接使用的工作報告。

**Positioning:** 這份報告是 **rule-driven operational baseline report**，不是週一市場開啟後的 live validation report。它必須清楚區分：

- 已經在 `main` 落地的 `v1.4.8` close control plane 行為
- 依照現行規則與資料結構推導出的高真實度交易情景
- 仍需等週一運行驗證的 runtime 表現

---

## 1. Why This Report Exists

`v1.4.7` 已經把 entry 端做成 control plane；`v1.4.8` 則把 close domain 收斂成單一 execution / verify / reconcile 路徑。這代表現在需要一份不是 changelog、不是功能清單，而是能讓人理解「倉位實際是怎麼被管理、怎麼被關掉、怎麼留下證據」的操作型報告。

本報告的作用有三個：

1. 作為 `v1.4.8` close-domain 行為的可閱讀基準
2. 作為 `v1.4.9` bugfix / 微調的討論底稿
3. 作為 `v1.5.0` 進一步做 memory quality、exposure budget、cross-repo contract freeze 的邏輯起點

---

## 2. Structure

報告沿用 `docs/PropFirmPilot_v1.4.7_Report.md` 的總體形狀，但加強數字密度與 close-domain 語義深度。

### Part A — 報告定位

要回答：

- `v1.4.8` 與 `v1.4.7` 的關係
- 為何這份文件不是 live 績效證明，而是 rule-driven baseline
- `qlib_market_scanner`、`TradingAgents`、`prop-firm-pilot` 在 close-domain 各自扮演什麼角色

### Part B — Close Control Plane 標準主流程

要用一條標準主流程描述：

1. scanner 產生候選
2. `TradingAgents` 產生方向與風險敘事
3. 倉位建立並進入 opened lifecycle
4. tactical entry context 持續作為持倉背景
5. tactical exit / reduce exposure / re-eval / emergency / best-day 產生 `CloseIntent`
6. `CloseControlPlane.execute()` 產生 `CloseOutcome`
7. broker write 與 verify / pending reconcile 分離
8. `CloseReconciler.reconcile()` 產生 canonical `final_close_reason`
9. `CLOSE_CONTROL_EVENT` 與 `TRADE_CLOSED` 形成學習與審計輸出

### Part C — 12 個細顆粒交易情景

每個情景都必須帶固定數字欄位，至少包含：

- `entry price`
- `initial SL`
- `initial TP`
- `lot`
- `5m realized vol`
- `1m ATR`
- `5m ATR`
- `spread`
- `partial close volume`
- `breakeven trigger`
- `trailing level`
- `close price`
- `realized pnl`
- `trigger_source`
- `action_kind`
- `final_close_reason`
- `resolution_path`

每個情景都要明確寫出：

- scanner 與 `TradingAgents` 的介入點
- tactical module 做了什麼操作
- broker write 只代表 submitted / accepted / verify result，不能混寫成已平倉
- reconciler 最後如何定義 `final_close_reason`

### Part D — 可持續學習 / Audit Trail / 後續缺口

要拆成五段：

1. 可持續學習性
2. audit trail
3. 對 `v1.4.9` 的直接 baseline
4. 對 `v1.5.0` 的邏輯 baseline
5. 術語速覽

## 3. Scenario Set

以下 12 個情景已確認納入，不能刪改主題，只能微調數值與敘述：

1. `EURUSD` 倫敦盤突破多單，`+1.0R` 做 `partial_close`，餘倉 trail，最後 `tp_hit`
2. `GBPUSD` 紐約盤回撤空單，先 `MOVE_TO_BREAKEVEN`，之後回抽打到 `sl_hit`
3. `USDJPY` 趨勢延續多單，`TRAIL_SL` 連續上移兩次，最後 trail 保利出場
4. `AUDUSD` 震盪盤多單，`REPRICE_TP` 下調目標，縮短持倉時間後獲利出場
5. `NZDUSD` 反轉風險加劇，tactical 直接 `EXIT_NOW`，走 `full_close`
6. `EURUSD` 高波動回吐，`modify_only` broker write 成功但 verify mismatch，後續仍被原始保護單打掉
7. `GBPUSD` drawdown 進入 `DANGER`，系統做 `reduce_exposure` partial close，之後剩餘倉位回升
8. `USDCHF` 進入 `CRITICAL`，`emergency_close` 同時處理兩筆倉位
9. `EURUSD` 持倉期間 LLM re-eval 翻向，觸發 `reeval_close`
10. `GBPJPY` Best Day Rule 保護，系統只關閉浮盈倉位，鎖定日內已得利潤
11. `AUDUSD` broker-side / manual detected close，control plane 以 `manual_or_broker` reconcile
12. `USDCAD` 外部關倉且 broker closed row 延遲，靠 `execution_meta + last_known_profit` 完成 final reconciliation

## 4. Required Alignment With Actual Code

報告中的 close semantics 必須對齊實作，不可自行發明：

### `CloseControlPlane.execute()`

- `modify_only`
  - broker modify fail -> `execution_status="skipped"` / `readback_status="not_needed"`
  - modify success but verify fail -> `execution_status="verify_failed"` / `readback_status="mismatch"`
  - verify success -> `execution_status="accepted"` / `readback_status="verified"`
- `partial_close` / `full_close`
  - duplicate pending close -> `skipped / not_needed`
  - broker close success -> `submitted / pending_reconcile`

### `CloseReconciler.reconcile()`

- 預設 `trigger_source="manual_or_broker"`
- 預設 `action_kind="external_detected_close"`
- `final_close_reason` 優先序：
  - `emergency_close`
  - `best_day_close`
  - `reeval_close`
  - broker `TAKE_PROFIT` -> `tp_hit`
  - broker `STOP_LOSS` -> `sl_hit`
  - broker `STOP_OUT` -> `broker_stopout`
  - close-price proximity to TP / SL
  - PnL sign fallback
  - `manual_close`
- `resolution_path`
  - `broker_api`
  - `best_day_close`
  - `reeval_close`
  - `execution_meta`
  - `last_known_profit`
  - `unknown`

### Scheduler Event Payloads

- `CLOSE_CONTROL_EVENT`
  - `position_id`
  - `intent_id`
  - `symbol`
  - `trigger_source`
  - `action_kind`
  - `execution_status`
  - `readback_status`
  - `final_close_reason`
  - `reason_code`
  - `broker_success`
  - `broker_message`
- `TRADE_CLOSED`
  - `intent_id`
  - `symbol`
  - `position_id`
  - `pnl`
  - `reason`
  - `trigger_source`
  - `action_kind`
  - `final_close_reason`
  - `resolution_path`

---

## 5. Language And Tone

這份報告的風格要求：

- 預設繁體中文
- 第一個專業術語出現時，後面要跟一個簡單中文說明
- 偏 operator / architect 語氣
- 不寫成 marketing
- 不假裝是 market-open live result
- 儘量把 close-domain 操作講成「誰發起、系統做什麼、broker 回什麼、最後怎麼定性」

---

## 6. Success Criteria

報告完成後，應能讓讀者直接回答以下問題：

1. `v1.4.8` 的 tactical / emergency / reduce exposure / reeval / best-day / external close，現在是否都進了同一套 close control plane
2. `modify_only`、`partial_close`、`full_close`、`external_detected_close` 的差異是什麼
3. 為什麼 `submitted` 不等於已平倉
4. 一筆單從 scanner 到 final close reason 的完整鏈路長什麼樣
5. `CLOSE_CONTROL_EVENT` 與 `TRADE_CLOSED` 為什麼能作為後續學習與審計基底
6. `v1.4.9` 與 `v1.5.0` 下一步應該優先補哪裡
