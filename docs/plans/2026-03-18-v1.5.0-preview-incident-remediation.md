# v1.5.0 Preview Incident Postmortem

**Date:** `2026-03-18`  
**Incident Window:** `2026-03-17` to `2026-03-18` (UTC+8, based on `prod_logs_20260318_v1.5.0_preview`)  
**Runtime:** `v1.5.0_preview`

## Executive Summary

在 `2026-03-17` 至 `2026-03-18` 的 production 視窗內，`v1.5.0_preview` 進入「系統大致在線，但實際上無法形成健康新單流程」的退化狀態。最嚴重的 P0 問題是 `Best Day Rule` 在實際 `0` 交易、`0` 當日 PnL 的情況下仍阻擋新單，原因是系統錯把未發生的 hypothetical TP profit 當成當日已實現風險暴露。這個判定在業務語義上完全錯誤，也直接導致 deterministic false reject。

同一時段內，incident bundle 亦顯示 market-data 與 tactical layer 有多個疊加性問題：websocket failure `15` 次、REST fallback warning `129` 次、`market_data.quote_unavailable` 在 log 與 journal 各出現 `2` 次；tactical hard-gate 中 `spread.fail.ratio_too_wide` 出現 `72` 次、`atr.fail.insufficient_1h_data` 在 hard-gate payload 中出現 `133` 次。這些訊號說明問題不是單一 provider outage，而是錯誤 gate、過晚的 compliance admission、websocket-first 架構、與過寬的 success semantics 同時放大了 incident。

本輪 remediation 的核心決策如下：

- `Best Day Rule` 改為 actual-daily-PnL-only，禁止再用 projected profit 阻擋 no-trade state。
- compliance headroom 前移到 candidate / intent creation，避免必定被拒的單子仍跑完整個 tactical / execution 流程。
- market-data routing 改為 `broker quote-first + API bars-first + websocket auxiliary`。
- scanner success contract 收緊為「process success + artifact success + ingestion success + target_date matched」。
- Telegram alerting 補上 retry accounting 與 secondary sink，避免 incident 期間告警本身消失。

## Customer Impact

- 新單在本應可交易的狀態下被錯誤阻擋，直接壓低策略實際參與市場的能力。
- deterministic compliance reject 沒有在 admission stage 被攔下，造成 scanner candidate、LLM、tactical retry、execution compliance 的無效 churn。
- USDCAD tactical path 長時間處於近乎不可通過狀態，bundle evidence 顯示主要硬阻塞為 spread ratio 與 ATR 1H warmup。
- market-data architecture 對 websocket 依賴過重，導致 provider 退化時整體系統可交易性被放大為更嚴重的 block。
- scanner process exit code 為 `0` 時曾被過早記錄為成功，即使 target date 並未真正落盤。
- Telegram outbound timeout 期間，primary alert channel 可短暫失效，增加 operator 對 incident 狀態的觀測盲區。

## Root Cause

### 1. Incorrect Best Day Semantics

`Best Day Rule` 的 pre-trade gate 錯把 hypothetical TP potential profit 納入當日 PnL。這使得「尚未發生的理論獲利」被當成已發生的當日結果，進而在 `daily_pnl=0`、`open_positions=0` 的情境下直接阻擋新單。這是本次 incident 中最直接、最不可接受的 correctness defect。

### 2. Compliance Headroom Checked Too Late

deterministic compliance headroom 原本在 execution 前才被檢查，導致必定失敗的 candidate 仍先建立 intent、可能進入 LLM worker、再進 tactical / execution pipeline。這不是 safety hole，但它放大了 incident 的成本與噪音。

### 3. Tactical Hard Blocks Were Compressed Into Insufficient Diagnostics

tactical verdict 雖然實際同時受 spread 與 ATR warmup 影響，但舊 payload 多半只保留單一 summary reason。incident review 因此難以直接分辨：

- 這是 `spread < 2.0x limit` 的 calibration 問題
- 還是 `atr.fail.insufficient_1h_data` 的暖機條件問題
- 抑或 freshness 真正失敗

bundle evidence 顯示 `data_freshness` 並不是主阻塞，真正的主阻塞是 spread 與 ATR 1H warmup。

### 4. Websocket-First Architecture Overweighted an Unstable Auxiliary Feed

incident bundle 內已觀察到 websocket repeated degradation，但舊 routing 仍讓 websocket 承擔 primary live path 的決定性角色。由於 `EODHD LIVE API` 為 delayed 1 minute，API 不適合作為 live quote primary；因此正確修法不是「純 API-first」，而是：

- `broker quote-first` for live quote / spread
- `API bars-first` for closed `1m/5m/1h` bars
- `websocket auxiliary` for telemetry / cache / non-primary fallback

### 5. Scanner Success Was Declared Before Ingestion Contract Was Proven

`ScannerBridge.run_pipeline()` 原本只要 subprocess exit code 為 `0` 就先記 `pipeline finished successfully`，之後才讀 signals bundle 與驗證 `target_date`。這讓「process success」被誤當成「pipeline success」，與 live ingestion contract 不一致。

### 6. Alert Delivery Had No Real Secondary Path

Telegram send path 雖然已有 circuit breaker 雛形，但沒有 retry accounting，也沒有 circuit-open 期間的 alternate sink。當 primary send timeout 或 circuit open 時，告警可能直接消失，讓 incident 當下的操作可見性下降。

## Exit Criteria

- 不再出現 no-trade / zero-PnL state 被 `Best Day Rule` 錯殺。
- candidate-to-intent conversion 不再包含明知會被 compliance deterministic reject 的單子。
- websocket degraded 時，只要 broker quote 與 API bars 可用，entry path 仍可正常工作。
- scanner 不再把缺少 `target_date` 的 bundle 記成成功。
- Telegram primary send 失敗時，重試與 alternate sink 會留下可觀測足跡。
