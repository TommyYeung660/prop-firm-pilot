# v1.5.0_beta_2 Design

**Date:** `2026-03-17`

**Goal:** 把 `v1.5.0_beta` 在 production 長跑中暴露的 P0 / P1 operational 問題收斂成一個完整可落地的修復版 `v1.5.0_beta_2`，只修 correctness 與穩定性，不混入 capital-efficiency 優化。

## Context

- `v1.5.0_beta` 已完成 scanner runtime bundle contract 與 market-data freshness 第一輪整合。
- `2026-03-16` 晚到 `2026-03-17` 上午的 production run 顯示，系統仍存在幾個會直接影響 live correctness 的缺口：
  - scanner target date 缺失時仍可能 fallback 到 latest stale signals
  - tactical pending 的 retry budget 與 claim TTL 不一致，會被 janitor 提前收掉
  - Telegram tactical gate 通知無節流，operator noise 過高
  - `EquityMonitor` 寫入 snapshot 時可能撞到 sqlite transaction overlap
  - EODHD WebSocket `keepalive ping timeout` 後只做 reconnect，沒有把 feed 退化狀態明確反映到 entry guard
- 使用者已明確確認：
  - `v1.5.0_beta_2` 視為這一輪完整落地版本
  - `資金使用率偏低` 不屬於 `beta_2`，改在 `v1.5.0_stable` 作 bounded optimization
  - 當 signals 不 fresh 或 market data 退化到只剩 stale REST bars 時，只阻擋新 intents / 新開倉；持倉監控、tactical exit 與 drawdown 保護要照常運作

## Approved Direction

採用「協調式 hardening」：

1. 在 entry path 的最上游做 hard block，阻止 stale signal / degraded live data 進入新開倉流程。
2. tactical pending lifecycle 改為 deterministic deadline control，不再依賴 janitor 與 claim TTL 偶然對齊。
3. alert 與 incident diagnostics 走現有 scheduler / trade-event 管道補強，不引入新的大型 observability subsystem。

## Design

### 1. Scanner target-date strictness

- 修改 `src/signal/scanner_bridge.py`
- live path 只接受 `signal_date == request_date` 的 scanner bundle
- 當 `target_date` 缺失時：
  - 不再 fallback 到 latest date signals
  - 設定 rejection code，例如 `scanner.bundle.target_date_missing`
  - 回傳空 signals，讓 scheduler 明確停在 non-tradable state
- cache 只允許 fresh target-date results 進入；stale 結果最多保留 rejection / diagnostics，不可成為同日交易 cache

### 2. Entry-safe market-data gating

- 修改 `src/data/fx_websocket_client.py` 與 `src/data/market_data_hub.py`
- WebSocket client 補強 runtime health state：
  - 追蹤 `last_error`
  - 追蹤連續 reconnect / disconnect 次數
  - 將 `keepalive ping timeout`、長時間無 tick、握手失敗統一映射到明確 degraded state
- MarketDataHub 暴露可供 scheduler 判斷的 feed status：
  - websocket health
  - forced stale symbols
  - REST fallback freshness
- Scheduler 在新 intents / 新開倉前檢查：
  - scanner signals 是否 fresh
  - live tactical quote / bars 是否 usable
  - 若 websocket degraded 且 REST fallback 仍 stale / missing，直接 block entry
- exit path、持倉監控、drawdown 保護維持現有 fallback，避免因資料退化失去風控能力

### 3. Tactical pending deterministic lifecycle

- 修改 `src/scheduler/scheduler.py`、`src/decision_store/sqlite_store.py`、必要時 `src/config.py`
- 根因是 tactical retry budget 目前可能長於預設 `claim_ttl_minutes`
- 修復策略：
  - 進入 `tactical_pending` 時就計算完整 retry window 的 deadline
  - 將 `expires_at` 對齊 tactical retry budget，而不是沿用原始 claim TTL
  - janitor 只會在這個 deadline 之後將 intent 收斂成 terminal state
- 這讓 `WAIT -> PASS / DEGRADE / CANCEL / TIMED_OUT` 的 state transition 變成 deterministic，不再發生 retry 還沒跑完就被 recycle 的情況

### 4. Telegram tactical gate throttling

- 修改 `src/scheduler/scheduler.py`
- `TACTICAL_RESULT` trade event 仍完整保留
- Telegram alert 增加 keyed throttling / dedupe：
  - 第一次 WAIT 立即發送
  - 狀態改變時發送
  - 最終 resolution 發送
  - 相同內容只保留低頻 heartbeat
- 目標是降低 operator 噪音，不犧牲 postmortem 可追溯性

### 5. Incident diagnostics closure

- 修改 `src/scheduler/scheduler.py` 與可能的 store / journal payload
- 在既有 event / log payload 補充：
  - `request_date`
  - `signal_date`
  - `scanner_rejection_reason`
  - `feed_state`
  - `ws_last_error`
  - `quote_source`
  - `bar_sources`
  - `entry_block_reason`
  - `tactical_deadline_at`
- 先利用既有結構完成 operator triage，避免為了 observability 再開新 subsystem

### 6. Equity snapshot transaction consistency

- 修改 `src/decision_store/sqlite_store.py`
- `insert_equity_snapshot()` 納入既有 `_write_lock` 與一致的 transaction 邊界
- 避免 `asyncio.to_thread()` 背景寫入與其他 store write 共用同一 sqlite connection 時觸發 `cannot start a transaction within a transaction`

## Error Handling

- `entry path` 採 fail-closed：
  - fresh signals 缺失
  - websocket feed degraded
  - REST fallback stale / missing
  - 上述任一條件滿足即 block 新 intents / 新開倉
- `exit path` 與持倉風控採 fail-operational：
  - tactical exit 仍盡量使用 hub fallback / broker quote 執行
  - drawdown monitor 不因 entry block 而停擺
- 所有 block / degrade / timeout 都需留下 deterministic reason code，避免 operator 只能從自由文字猜測

## Testing

1. `tests/test_scanner_bridge.py`
   - target date 缺失時不再 fallback
   - stale bundle 不進 live cache
   - rejection code / message 正確
2. `tests/test_scheduler.py`
   - scanner stale / missing 會 block new intents
   - websocket degraded + stale REST 會 block entry，但不影響 tactical exit path
   - tactical pending retry window 不會被 janitor 提前收斂
   - Telegram tactical gate 會節流 / 去重
   - incident payload 帶出新的 diagnostics fields
3. `tests/test_alert_service.py`
   - 視 scheduler alert path 需求補 alert 互動測試
4. store / websocket / market-data 相關測試
   - sqlite equity snapshot 在並行寫入下維持穩定
   - websocket ping timeout / reconnect 會映射到 feed degraded state

## Non-Goals

- 不處理 `資金使用率偏低`
- 不做完整 capital-efficiency / portfolio allocation refactor
- 不做新的 observability platform
- 不改 scanner runtime default cadence

## Acceptance Criteria

- 新 UTC 日找不到 target-date signals 時，不會再建立 live tradable intents
- websocket 長時間退化且 REST bars stale 時，系統明確 block 新 entry
- tactical pending path 能 deterministic 收斂，不再靠 expired-claim recycle 漂移
- `EquityMonitor` 多小時運行不再出現 sqlite transaction overlap
- Telegram tactical gate 通知量顯著下降，但 trade events 仍完整可追溯
