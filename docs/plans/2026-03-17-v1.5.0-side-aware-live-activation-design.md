# v1.5.0 Side-Aware Live Activation Design

**Goal:** 讓 `qlib_market_scanner -> prop-firm-pilot -> TradingAgents -> execution` 這條 live 路徑正式吃到顯式方向的 FX scanner candidates，並以 `topk_short = 1` 啟用第一批真實 short 流量。

**Context**

- `qlib_market_scanner` 已具備 `fx_signal_v2` side-aware export contract，CSV/JSON 都能表達 `side=long|short`，但 runtime 仍固定 `configured_topk_short = 0`，尚未對 live 發布 short rows。
- `prop-firm-pilot` 目前只接受 `fx_signal_v1`，`ScannerBridge` 不認得 `side`，`TradeIntent` 與 SQLite 也沒有 `scanner_side`。
- scheduler 目前是 long-only 假設：
  - scanner loop 以 `symbol` 為粒度去重，再依 raw `score` 高低排序
  - pre-filter / post-filter / decision formatter 把 `scanner_score` 直接視為品質分數
  - decision cache key 不含方向
  - duplicate intent guard 只看 `symbol + trade_date + source`
- 如果直接打開 short rows，但不改 pilot，下游會把低分 short candidate 當成「低品質多頭」，導致 short 被錯誤 pre-filter、排序或 cache 命中。

**Approach Options**

1. 只做 bridge 相容，live 不開 short
   - 優點：最穩，幾乎不改交易行為。
   - 缺點：無法真正驗證 short alpha 與下游流程。

2. side-aware ingestion 但 short 只做影子記錄
   - 優點：可先觀察 short 流量與 LLM 反應。
   - 缺點：仍不是 live activation，交易結果不會反映新契約。

3. end-to-end live activation with directional normalization
   - 優點：scanner 的 `SELL` candidate 真的進入決策與交易流，方向語義終於一致。
   - 缺點：必須同時修正排序、threshold blending、cache key、DB schema 與 cross-repo runtime activation。

**Chosen Design**

採用方案 3，並把第一階段 live short 發布量限制為 `topk_short = 1`。

1. Cross-repo activation boundary
   - `qlib_market_scanner` 新增 `topk_short` config / CLI / runner 傳遞。
   - scanner 專案的安全預設維持 `topk_short = 0`，避免單獨執行時意外開 short。
   - `prop-firm-pilot` 新增 `scanner.topk_short`，並在 live scanner subprocess 明確傳 `--topk-short 1`。
   - 啟用 short 的主控權放在 pilot，而不是分散在 scanner repo 預設值。

2. Contract and compatibility
   - `prop-firm-pilot` 同時接受：
     - `fx_signal_v1`：legacy long-only / direction-implicit
     - `fx_signal_v2`：direction-explicit
   - `v2` bundle 進 pilot 時：
     - `side` 是正式契約欄位
     - scheduler 以 scanner side 為真，不再讓下游自行猜方向
   - `v1` bundle 仍可讀，但保留 legacy 行為：
     - `scanner_side = None`
     - raw `score` 仍視為品質分數

3. ScannerBridge semantics
   - `ScannerSignal` 新增 `side`。
   - `to_qlib_data()` 額外帶：
     - `scanner_side`
     - `scanner_direction_quality`
   - directional quality 定義：
     - `long -> quality = score`
     - `short -> quality = 1 - score`
     - `legacy / unknown -> quality = score`
   - `load_signals_from_file()` 對 `v2` 要求 `side` 合法；對 `v1` 不要求。

4. TradeIntent and persistence
   - `TradeIntent` 新增 `scanner_side: Literal["long", "short"] | None`。
   - SQLite `intents` table 新增 `scanner_side` 欄位，使用 idempotent migration。
   - 既有資料允許 `NULL`，確保舊 DB 可平滑升級。
   - `intent_exists()` 改成可選 side-aware 查詢：
     - 若傳入 `scanner_side`，就以 `(symbol, trade_date, source, scanner_side)` 判斷
     - 若 `scanner_side is None`，保留 legacy `(symbol, trade_date, source)` 邏輯

5. Scheduler scanner ingestion
   - 對 `v2` signals：
     - 不再做「每個 symbol 只留最高 raw score」的 long-only 去重
     - 改為以 `(symbol, scanner_side)` 為粒度去重
     - 候選排序改用 `scanner_direction_quality`，而不是 raw `score`
   - 對 `v1` signals：
     - 保留現行 per-symbol / raw-score 流程
   - `INTENT_CREATED` event、Telegram alert、memory context 一律帶 scanner side。

6. LLM and threshold semantics
   - pre-filter / post-filter / decision formatter 一律改用 directional quality：
     - `long: score`
     - `short: 1 - score`
   - decision cache key 必須納入 `scanner_side`，避免 long / short 錯誤共用 cache。
   - `qlib_data` 明確帶入 `scanner_side`，讓 TradingAgents 接到的是「某方向 candidate」，不是無方向 symbol。
   - agent decision 若與 scanner side 相反：
     - `scanner_side=long` 但 agent 回 `SELL`
     - `scanner_side=short` 但 agent 回 `BUY`
     - 一律視為 `direction_mismatch`，取消 intent，不允許逆向下單
   - TradingAgents 在這個版本的角色是「確認或否決方向」，不是替 scanner 猜方向。

7. Risk and execution constraints
   - `has_active_position_for_symbol(symbol)` 仍維持 symbol-level hard gate。
   - 不允許同一 symbol 同時持有 opposite-side live positions。
   - `same_direction_limit` 仍以 execution side (`BUY/SELL`) 計數即可，不需要另開 scanner-side limit。
   - 這次不引入 hedge / netting / opposite-position coexistence。

8. Initial live activation
   - 啟用設定：
     - `scanner.topk = 3`
     - `scanner.topk_short = 1`
   - 預期 live scanner 每次最多輸出：
     - 3 個 long candidates
     - 1 個 short candidate
   - 若 capacity 不足，scheduler 以 directional quality 競爭剩餘 slot。
   - short candidate 不是保留名額，而是與 long candidates 共同比較 quality。

9. Observability
   - 新增或延伸以下觀測欄位：
     - `scanner_side`
     - `scanner_direction_quality`
     - `threshold_source`
     - `threshold_min_confidence`
     - `threshold_min_blended_confidence`
   - 觀測重點：
     - long / short created intent counts
     - direction mismatch cancel rate
     - short pre-filter cancel rate
     - short tactical reject rate
     - short opened trade count and pnl

10. Rollback
   - 快速回滾路徑：
     - 將 `prop-firm-pilot` 的 `scanner.topk_short` 改回 `0`
     - 保留 bridge / DB / scheduler side-aware code，不回退 schema
   - 如需契約回滾：
     - pilot 仍能吃 `fx_signal_v1`
     - scanner repo 可停用 `--topk-short`
   - 這樣可在不做 DB rollback 的前提下立刻停止 live short 流量。

**Non-Goals**

- 不在這次加入同 symbol opposite-side hedge。
- 不重新設計 TradingAgents prompt 或 analyst 組合。
- 不重做 compliance / execution sizing 規則。
- 不把 short candidate 保證保留一個 execution slot。
