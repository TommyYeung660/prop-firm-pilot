# v1.5.x Single-Entry Roadmap Design

> **Date:** `2026-03-16`
> **Status:** Approved
> **Scope:** `prop-firm-pilot` roadmap consolidation

## Goal

建立單一入口文件 `docs/PropFirmPilot_v1.5.0_road_map.md`，讓操作者與開發者只看這一份，就能回答：

- `v1.5.0 stable` 已經做了什麼
- `v1.5.0 stable` 還缺什麼
- `v1.5.1` 到 `v1.5.9` 應該怎樣分波段推進
- 哪些工作屬於 cross-repo 依賴，而不是 `prop-firm-pilot` 單 repo 可完成

## Problem

目前 `v1.5.0` 相關敘事分散在多份文件：

- `docs/PropFirmPilot_v1.5.0_Profitability_Outlook_Report.md`
- `docs/PropFirmPilot_v1.4.0_road_map.md`
- `docs/PropFirmPilot_changelog.md`
- `docs/PropFirmPilot_v1.5.0_beta_Deployment_Manual.md`
- `docs/PropFirmPilot_v1.5.0_beta_Acceptance_Baseline.md`

這些文件各自有價值，但用途不同。結果是：

1. `v1.5.0 stable` 已完成與未完成項目沒有被集中列出
2. `v1.5.x` 容易被誤解成「任意新功能桶」
3. cross-repo 依賴雖然存在，但沒有被放進單一版本規劃中

## Chosen Approach

採用 **版本主軸 + 波段分工**：

1. 文件主體直接按 `1.5.0` 到 `1.5.9` 展開
2. `1.5.1-1.5.3`、`1.5.4-1.5.6`、`1.5.7-1.5.9` 形成三個波段
3. 每個版本都固定寫：
   - 版本定位
   - 本 repo 主責
   - cross-repo 依賴
   - 明確不做什麼
   - 完成條件

## Design Decisions

### 1. 先做現況盤點，再排版本

文件前段先把內容切成四類：

- 已完成，無需再規劃
- 屬於 `v1.5.0 stable` 必須完成
- 明確延後到 `v1.5.x`
- 明確不屬於 `1.5.x`

這能讓文件本身先回答 review 問題，而不是只給未來規劃。

### 2. `v1.5.0` 定位為 stable gate closure

`v1.5.0_beta` 已經把 scanner contract freeze、version identity、`1d` canonical cadence 吸收入主線。

因此 `v1.5.0 stable` 不應再被寫成「重新設計 scanner cadence」或「全面重做系統」，而應是：

- tactical entry / exit reliable closure
- memory v1 closure
- exposure guard v1 closure
- multi-day validation closure

### 3. `1.5.x` 維持 validation-first，而不是 feature-first

雖然 `1.5.x` 仍會有功能工作，但主軸不是大規模新產品，而是：

- bugfix
- consistency hardening
- validation accumulation
- bounded follow-up research productization

這與盈利報告中的保守結論保持一致。

### 4. 直接寫入 cross-repo 依賴

因為使用者要求「不用再看複數文檔」，所以 roadmap 內要直接標示：

- 哪些項目需要 `qlib_market_scanner`
- 哪些項目需要 `TradingAgents`
- 哪些項目在 `prop-firm-pilot` 內只能做接口與 gate，不能單獨宣稱完成

## Expected Outcome

完成後的 `docs/PropFirmPilot_v1.5.0_road_map.md` 應能作為：

- `v1.5.0` 到 `v1.5.9` 的唯一版本規劃入口
- stable / post-stable / follow-up research 的邊界說明
- 開發優先級排序依據
- cross-repo release conversation 的共通語言

## Non-Goals

- 不重寫盈利報告全文
- 不取代 changelog 的發版記錄功能
- 不把 `1.5.4+` 之後的版本寫成不可調整的硬性承諾
