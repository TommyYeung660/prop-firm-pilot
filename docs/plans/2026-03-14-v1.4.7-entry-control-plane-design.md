# v1.4.7 Tactical Entry Control Plane Design

**Version Target:** `v1.4.7`

**Goal:** 將 tactical entry 從「可運行」提升為「可回放、可校準、可運維」的 entry control plane，讓每次 entry verdict 都能被 deterministic 地解釋、重播與分析。

**Scope:** 聚焦 `prop-firm-pilot` 的 tactical entry validator / scheduler lifecycle / journal & metrics diagnostics / scanner-to-pilot contract；不修改 tactical exit policy、execution engine 下單語義、LLM thesis 邏輯或 compliance 規則。

---

## 1. 背景與問題

roadmap 已將 `v1.4.7` 明確定義為 **Tactical Entry Fixes & Optimization**。目前系統已具備：

- tactical validator gate 雛形
- `claimed -> tactical_pending -> ready_for_exec / timed_out` lifecycle 骨架
- `quote_source / bars_5min_source / bars_1h_source / data_source` 基本 provenance
- trade journal event 與 operational metrics 記錄能力

但 entry path 仍有三個結構性缺口：

1. tactical verdict 仍偏向「字串 + log」，缺乏 deterministic reason taxonomy
2. `WAIT / degrade / timed_out / cancelled` 雖已存在骨架，但語義與狀態轉移仍不夠一致
3. mixed-source freshness、fallback、session/regime 差異尚未沉澱為可供 calibration 的結構化資料

結果是：

- postmortem 仍需肉眼拼 logs
- false WAIT 與資料問題不易分辨
- calibration 缺乏可信輸入
- 下一版若要做 exit hardening，仍可能回頭補 entry metadata

---

## 2. 設計目標

### 2.1 Functional Goals

- 每次 tactical entry verdict 都能回答「為什麼進、為什麼等、為什麼跳過」
- lifecycle 由 verdict 語義驅動，而不是 scattered if/else
- mixed-source / fallback / freshness 進入結構化 diagnostics
- 產出可供 `symbol / session / regime` 切片分析的 calibration 輸出

### 2.2 Engineering Goals

- 保留現有 pipeline 主狀態集合，避免無必要的 DB state 擴張
- 優先 journal-first，將完整 verdict bundle 落盤為單一事實來源
- 讓 scheduler、alert、metrics、postmortem 共用同一套 outcome 語義

### 2.3 Non-Goals

- 不改 tactical exit / SL / TP / emergency close policy
- 不改 execution engine 的執行語義
- 不改 LLM 的 strategic thesis / prompting
- 不在 `v1.4.7` 直接做 runtime 自動 tactical threshold 調參

---

## 3. Architecture / Scope Boundary

`v1.4.7` 將 tactical entry 定義為一個 **entry control plane**，位置仍介於 strategic decision 與 execution 之間，但責任提升為：

1. 產生可重播的 entry verdict
2. 用統一 verdict 語義驅動 lifecycle
3. 為營運與 calibration 保留完整 provenance 與 diagnostics

設計上拆成四個層次：

### 3.1 Verdict Schema

validator 不再只回傳 `PASS / WAIT / REJECT`，而是回傳完整 verdict bundle，至少包含：

- action
- resolution
- reason codes
- gate breakdown
- threshold snapshot
- market/data provenance
- session/regime context
- retryability hints

### 3.2 Lifecycle Policy

scheduler 只根據 verdict resolution 決定狀態轉移，不再自行拼接多套 tactical policy。這讓 `WAIT / degrade / timed_out / cancelled` 具備固定語義。

### 3.3 Provenance Bundle

candidate metadata、scanner score、quote/bars source、rescan trigger、freshness basis、decision cache hit、shadow/enforced mode 進入同一 bundle，供 journal、alert、postmortem、calibration 共用。

### 3.4 Calibration Output

先輸出穩定的 entry verdict 資料，不在本版直接線上自動調參。先觀測，再調整。

---

## 4. Entry Lifecycle / State Machine

本版不新增新的持久化主狀態，沿用現有：

- `pending`
- `claimed`
- `tactical_pending`
- `ready_for_exec`
- `executing`
- `opened`
- `cancelled`
- `timed_out`

關鍵調整是將 tactical entry 的狀態語義固定化。

### 4.1 `claimed`

代表 strategic decision 已產生，但 tactical adjudication 尚未完成。每個 claimed intent 只允許進入一次初始 verdict 流程。

### 4.2 `claimed -> ready_for_exec`

兩種合法路徑：

- verdict `PASS`，resolution=`EXECUTE_NOW`
- verdict `WAIT` 經 policy 降級放行，resolution=`EXECUTE_DEGRADED`

`degraded` 不新增 DB status，而是以 metadata + event 呈現，避免擴大 migration 面。

### 4.3 `claimed -> tactical_pending`

只允許在 verdict resolution=`RETRY_PENDING` 時發生。這類 verdict 必須同時提供：

- 為何等待
- 等待的資料 / 條件
- retry 間隔
- retry 上限
- timeout / degrade 條件

### 4.4 `tactical_pending -> ready_for_exec`

兩種合法路徑：

- retry 後 verdict 轉為 `EXECUTE_NOW`
- retry 預算耗盡但 policy 允許，轉為 `EXECUTE_DEGRADED`

### 4.5 `claimed / tactical_pending -> timed_out`

只用於時間性失敗，例如：

- retry budget 耗盡且 expire_action=`cancel`
- tactical window 過期
- freshness 長時間無法恢復
- claim TTL 到期

這類情況語義是「來不及做」，不是「決定不做」。

### 4.6 `claimed / tactical_pending -> cancelled`

只用於非時間性 skip / abort，例如：

- LLM 最終 `HOLD`
- newer intent supersedes older intent
- session policy 禁入
- scanner contract 無效
- manual / risk abort

語義是「系統決定不做這筆」。

### 4.7 Verdict Resolution Layer

在 `action` 之外新增 resolution 語義：

- `EXECUTE_NOW`
- `RETRY_PENDING`
- `EXECUTE_DEGRADED`
- `SKIP_CANCEL`
- `EXPIRE_TIMEOUT`

這一層是 scheduler 的唯一 tactical lifecycle 入口。

## 5. Reason Taxonomy / Provenance / Diagnostics Schema

每次 tactical entry evaluation 都產生一份標準化 verdict bundle，分為五層。

### 5.1 Outcome Layer

回答這次 adjudication 的總結結果：

- `action`
- `resolution`
- `summary_reason_code`
- `detail`
- `retry_count`
- `shadow_mode`

### 5.2 Gate Breakdown Layer

每個 gate 都有固定欄位：

- `gate_name`
- `status` (`PASS` / `FAIL` / `SOFT_FAIL` / `DEGRADED` / `SKIPPED`)
- `reason_code`
- `observed_value`
- `threshold_value`
- `detail`

reason code 採 deterministic taxonomy，例如：

- `spread.fail.ratio_too_wide`
- `freshness.fail.timestamp_missing`
- `freshness.wait.quote_stale_retryable`
- `atr.fail.out_of_regime`
- `ema.soft_fail.misaligned`
- `candle.soft_fail.body_too_small`
- `candidate.fail.score_semantics_invalid`

### 5.3 Provenance Layer

回答這份 verdict 是用什麼資料與觸發來源做出的：

- `candidate_source`
- `scanner_score`
- `scanner_confidence`
- `scanner_score_gap`
- `scanner_drop_distance`
- `scanner_topk_spread`
- `rescan_trigger`
- `decision_cache_hit`
- `quote_source`
- `bars_5min_source`
- `bars_1h_source`
- `data_source`
- `quote_timestamp`
- `freshness_basis`
- `market_data_mode`

### 5.4 Context Snapshot Layer

回答當時的市場與策略上下文：

- `symbol`
- `side`
- `session_label`
- `regime_label`
- `scanner_timeframe`
- `market_event_context`
- `tactical_config_version`
- `threshold_profile_id`
- `evaluated_at`
- `tactical_window_age_seconds`

### 5.5 Policy Hints Layer

只供 scheduler 消費：

- `retryable`
- `degrade_allowed`
- `retry_interval_seconds`
- `retry_budget_remaining`
- `terminal_if_repeated`
- `skip_new_rescan`

### 5.6 Persistence Strategy

- **Full bundle:** 寫入 trade journal event，作為 replay / postmortem 的主資料源
- **Compact summary:** 寫入 decision record 的 compact JSON metadata，供 runtime / UI / quick lookup 使用

若本版不做新增 DB 欄位 migration，則先採 journal-first，decision record 僅存摘要版。

---

## 6. Calibration Outputs

本版 tactical calibration 採 **觀測先行，調參後置**。

### 6.1 Runtime 不做的事

- 不自動改 tactical gate threshold
- 不引入新的線上 optimizer
- 不直接把 calibration 結果接進 live gating

### 6.2 本版產出的資料

#### A. Entry Verdict Journal

完整 verdict bundle 寫入 journal，供 replay、incident review、memory ingestion 與後續分析使用。

#### B. Daily Entry Calibration Snapshot

按 `symbol / session / regime` 匯總：

- `pass_rate`
- `wait_rate`
- `degrade_rate`
- `timeout_rate`
- top reason codes
- retry success rate
- mixed-source ratio
- rest fallback ratio

#### C. Operational Metrics Extension

新增 tactical friction 指標，例如：

- `tactical_wait_count`
- `tactical_degrade_count`
- `tactical_timeout_count`
- `tactical_retry_success_count`
- `tactical_rest_fallback_wait_count`

---

## 7. Rollout Strategy

### 7.1 Phase 1: Schema-First

先導入 verdict schema、journal event、metrics breakdown，盡量維持 runtime tactical policy 等價，只先擴充觀測能力。

### 7.2 Phase 2: Lifecycle Tightening

將 scheduler 的 `WAIT / degrade / timed_out / cancelled` 全部改為根據 resolution 語義驅動，去除字串式 tactical policy 分支。

### 7.3 Phase 3: Calibration Export

基於穩定 journal 與 metrics，輸出 daily calibration snapshot，供之後 threshold 調整與運維分析使用。

---

## 8. 測試策略

### 8.1 Validator Schema Tests

驗證每種 gate verdict 都能產生固定：

- reason code
- threshold snapshot
- provenance 欄位
- resolution hints

### 8.2 Scheduler Lifecycle Tests

驗證：

- `PASS -> EXECUTE_NOW -> ready_for_exec`
- `WAIT -> RETRY_PENDING -> tactical_pending`
- `WAIT -> EXECUTE_DEGRADED -> ready_for_exec`
- `WAIT -> EXPIRE_TIMEOUT -> timed_out`
- 非時間性 skip -> `cancelled`

### 8.3 Source / Freshness Contract Tests

覆蓋：

- `websocket_cache`
- `warmup_cache`
- `rest_fallback`
- `mixed`
- quote timestamp present / missing
- bars only / quote only / partial data

確保 provenance 與 freshness basis 正確落進 verdict bundle。

### 8.4 Journal / Metrics Integration Tests

驗證：

- `TACTICAL_RESULT`
- `TACTICAL_PENDING`
- `TACTICAL_DEGRADED`
- timeout / cancel 事件
- daily metrics summary

都能穩定反映 tactical friction 分布。

---

## 9. 驗收標準

- 任一 entry intent 都能重播出單一、完整、結構化 verdict bundle
- 任一 `WAIT` 都能回答是否 retryable、等待什麼、何時 timeout 或 degrade
- mixed-source / rest fallback 進入可查詢統計，而非只存在 loguru 字串
- daily summary 能分開看到 `pass / wait / degrade / timeout / cancel`
- `v1.4.8` 做 exit hardening 時，不需要回頭補 entry metadata

---

## 10. 預期效果

設計完成後，entry path 的直接效果是：

- postmortem 不再依賴人工拼 logs
- `WAIT` 可以被拆解成健康等待與異常等待
- `degrade` 成為可衡量的 release mode，而非隱性放行
- calibration 首次擁有可信、可切片、可比較的輸入資料
- entry 與 exit 的版本邊界更清楚，`v1.4.7` 不會偷渡 exit policy 修改
